Lesson 43: Observability Logs, Metrics, Tracing, and Debugging Microservices

Welcome to one of the most important lessons in real backend engineering.

A beginner thinks:

“If my code works, my job is done.”

A production engineer thinks:

“How do I know my system is working when thousands of users are using it?”

In a monolith:

User

 |
 v

Application

 |
 v

Database

Debugging is simple.

You open logs:

ERROR at ProjectService.java:50

Done.

But in microservices:

User

 |
 v

Gateway

 |
 v

Project Service

 |
 v

Identity Service

 |
 v

Database

 |
 v

RabbitMQ

 |
 v

Notification Service

A request can travel through many systems.

Now the question becomes:

Where did it fail?

1. What is observability?

Observability means:

Understanding the internal state of a system by looking at its external outputs.

The three pillars:

1. Logs

2. Metrics

3. Traces

These are called:

The Three Pillars of Observability​

2. Logs

Logs tell you:

What happened?

Example:

2026-01-01 10:20:30

INFO

Project created successfully

projectId=10
userId=5

Another example:

ERROR

Database connection failed

service=project-service

Logs are events.

3. Why normal logs are not enough

Imagine:

User reports:

“Creating a project failed.”

You search:

project-service.log

You find:

Request received

Nothing else.

Why?

Maybe failure happened in:

Identity Service

or:

Database

or:

RabbitMQ

We need correlation.

4. Correlation IDs

A correlation ID is a unique identifier attached to a request.

Example:

requestId:

abc-123

Flow:

User Request

ID:
abc-123


        |
        v


Gateway

abc-123


        |
        v


Project Service

abc-123


        |
        v


Notification Service

abc-123

Now every log belongs to the same request.

5. Example logs without correlation ID

Bad:

Project created

Which user?

Which request?

Which service?

Unknown.

Better:

{
 "service":"project-service",
 "requestId":"abc-123",
 "userId":5,
 "action":"PROJECT_CREATED"
}

Now searchable.

6. Structured logging

Avoid:

System.out.println(
"User created project"
);

Better:

log.info(
"Project created id={} user={}",
projectId,
userId
);

Output:

Project created id=10 user=5

Even better:

JSON logs:

{
"time":"10:30",
"level":"INFO",
"service":"project-service",
"event":"PROJECT_CREATED",
"projectId":10
}

Tools can analyze these.

7. Centralized logging

In microservices:

You don’t want:

server-1
   |
   logs


server-2
   |
   logs


server-3
   |
   logs

You want:

                Services

                    |
                    v

            Log Collector

                    |
                    v

            Log Storage

                    |
                    v

            Search Dashboard

Common stack:

ELK

Elasticsearch
Logstash
Kibana

8. Metrics

Logs answer:

What happened?

Metrics answer:

How much is happening?

Examples:

Requests per second

CPU usage

Memory usage

Error rate

Response time

Example:

Project Service:

Requests:

5000/minute


Average latency:

120ms


Errors:

0.5%

9. Important backend metrics

Request count​

Example:

HTTP requests:

10000/min

Error rate​

Example:

500 errors:

2%

Latency​

Example:

95% requests < 200ms

Database metrics​

Example:

Active connections:

50

10. Prometheus

A popular metrics system.

Architecture:

Application

   |
   |
 exposes metrics

   |
   v

Prometheus

   |
   v

Grafana

Spring Boot provides:

Spring Actuator

11. Spring Boot Actuator

Dependency:

<dependency>

<groupId>
org.springframework.boot
</groupId>

<artifactId>
spring-boot-starter-actuator
</artifactId>

</dependency>

Now endpoints exist:

Example:

GET /actuator/health

Response:

{
"status":"UP"
}

Metrics:

GET /actuator/metrics

Example:

http.server.requests

jvm.memory.used

system.cpu.usage

12. Health checks

Very important.

Gateway asks:

Is Project Service alive?

Project Service:

{
"status":"UP"
}

But healthy means more than alive.

Example:

Application:

Running

Database:

Disconnected

Not healthy.

Health:

{
"status":"DOWN",

"database":"FAILED"
}

13. Kubernetes and health checks

Later, Kubernetes uses:

Liveness probe​

Question:

Is the application alive?

If no:

Restart it.

Readiness probe​

Question:

Can it receive traffic?

If no:

Remove it from load balancing.

Example:

Application starts

       |

Database unavailable

       |

Readiness = false

       |

No traffic sent

14. Distributed tracing

Now the third pillar.

Tracing answers:

What path did this request take?

Example:

User request:

GET /projects/10

Trace:

Gateway
 |
 | 20ms
 |
Project Service
 |
 | 50ms
 |
Identity Service
 |
 | 100ms
 |
Database

15. Trace vs Log

Log:

Database query failed

Trace:

This request spent:

Gateway:
10ms

Project:
50ms

Database:
900ms

Tracing finds bottlenecks.

16. OpenTelemetry

Modern standard:

OpenTelemetry

It provides:

  • tracing
  • metrics
  • context propagation

Architecture:

Application

 |
 v

OpenTelemetry Agent

 |
 v

Tracing Backend

17. Trace IDs

Similar to correlation IDs.

Example:

traceId:

xyz-999

Every service receives:

traceId=xyz-999

Flow:

Request

traceId=abc


Gateway

traceId=abc


Project Service

traceId=abc


Database

traceId=abc

User creates project:

  |
  | 5ms
  v

  |
  | 30ms
  v


PostgreSQL

  |
  | 10ms
  v


RabbitMQ Publish

  |
  | 2ms
  v

  |
  | 200ms
  v


Email Provider

Now we know:

Email provider was slow.

19. Logging + Metrics + Tracing together

Imagine:

Alert:

Error rate increased

Metrics tells:

Project Service
500 errors increased

Tracing tells:

Database calls are slow

Logs tell:

Connection timeout

Together:

You solve the problem.

21. Grafana

Grafana displays dashboards.

Example:

ProjectHub dashboard:

Requests/sec       5000

Error rate         0.2%

Average latency    120ms

Database CPU       60%

RabbitMQ messages  200

22. Alerts

Monitoring without alerts is incomplete.

Example:

Rule:

If error rate > 5%

for 5 minutes

send alert

Alert:

🚨 Project Service errors increased

23. Common production alerts

Application down​

Service unavailable

High latency​

95th percentile > 2 seconds

Database problems​

Connection pool exhausted

Queue problems​

RabbitMQ backlog growing

24. Debugging example

User:

“Project creation is slow.”

Without observability:

Guessing.

With observability:

Metrics:

Project API latency increased

Tracing:

Database query takes 3 seconds

Logs:

Slow query detected

Solution:

Optimize query.

27. Important production mindset

A service is not complete when:

Code works

It is complete when:

Code works

+

You know when it fails

+

You know why it fails

+

You can debug it quickly
