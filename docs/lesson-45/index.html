Lesson 45: Database Scaling Indexes, Read Replicas, Sharding, and High Traffic Design

Welcome to one of the most important backend engineering topics.

Until now, we improved performance using:

Client
 |
 v
Gateway
 |
 v
Service
 |
 v
Redis
 |
 v
Database

But eventually:

  • Redis is not enough
  • Database receives millions of requests
  • Tables contain billions of rows

Now we need database scaling.

1. The database scaling problem

Imagine ProjectHub grows:

Users:

10 million


Projects:

500 million


Tasks:

5 billion

Now this query:

SELECT *
FROM projects
WHERE owner_id = 100;

can become slow.

Why?

Because the database has to search a huge amount of data.

2. The first optimization: indexes

Before scaling databases, optimize queries.

An index is a data structure that helps the database find data faster.

Think of a book.

Without an index:

Read every page until you find the topic.

With an index:

Topic → Page number

You jump directly.

3. Without an index

Table:

projects

id | owner_id | name
--------------------
1  | 10       | App
2  | 20       | Shop
3  | 10       | Website
4  | 50       | CRM

Query:

SELECT *
FROM projects
WHERE owner_id = 10;

Database:

Check row 1
Check row 2
Check row 3
Check row 4
...

This is:

O(n)

4. With an index

Create:

CREATE INDEX idx_project_owner
ON projects(owner_id);

Now database maintains:

owner_id

10 → rows 1,3

20 → row 2

50 → row 4

Search becomes much faster.

5. Index types

B-Tree index​

Most common.

Good for:

=
<
>
BETWEEN
ORDER BY

Example:

WHERE created_at > '2026-01-01'

Hash index​

Good for exact matching:

WHERE email='john@test.com'

Full-text index​

For searching text:

Example:

"find projects containing Spring Boot"

6. What columns should be indexed?

Good candidates:

Frequently searched columns​

Example:

WHERE user_id = ?

Index:

user_id

Foreign keys​

Example:

project_members

project_id
user_id

Usually indexed.

Sorting columns​

Example:

ORDER BY created_at DESC

Index:

created_at

7. Do not index everything

Indexes have a cost.

Every index:

  • consumes storage
  • slows inserts
  • slows updates

Example:

Insert:

New project created

Database updates:

projects table

+

10 indexes

8. Composite indexes

Sometimes queries use multiple columns.

Example:

SELECT *
FROM tasks
WHERE project_id = 10
AND status='DONE';

Create:

CREATE INDEX idx_task_project_status
ON tasks(project_id,status);

Order matters.

This index helps:

WHERE project_id=10

and:

WHERE project_id=10
AND status='DONE'

but not necessarily:

WHERE status='DONE'

9. Query optimization

Bad:

SELECT *
FROM projects;

If you only need:

id
name

Do:

SELECT id,name
FROM projects;

Why?

Less data transferred.

10. Pagination

Bad:

SELECT *
FROM projects
LIMIT 50 OFFSET 1000000;

Problem:

Database still scans previous rows.

Better:

Cursor pagination.

Example:

SELECT *
FROM projects
WHERE id > 10000
ORDER BY id
LIMIT 50;

Meaning:

“Give me the next 50 after ID 10000.”

11. Database scaling types

There are two main approaches:

1. Vertical scaling

2. Horizontal scaling

12. Vertical scaling

Increase server power.

Example:

Before:

CPU: 8 cores
RAM: 32GB

After:

CPU: 64 cores
RAM: 256GB

Advantages:

  • simple
  • no application changes

Problems:

There is a limit.

You cannot buy an infinite machine.

13. Horizontal scaling

Add more database servers.

Example:

        Database


       +-------+

       |       |

       v       v


    Server1  Server2

Harder.

14. Read replicas

One of the most common strategies.

Most applications have:

Many reads

Few writes

Example:

ProjectHub:

Reads:

GET /projects
GET /profile
GET /tasks

Writes:

CREATE project
UPDATE task

Architecture:

                 Application


                     |

          +----------+----------+

          |                     |

          v                     v


       Primary             Replica


       WRITE               READ


          |
          |
       Replication

          |
          v

       Replica

15. How replication works

Primary:

INSERT INTO projects
VALUES (...)

Then:

Primary

   |
   |
 copies changes

   |
   v

Replica

16. Important: replication delay

Replicas are not always instant.

Example:

User creates:

Project A

Primary:

exists

Replica:

not yet updated

This is called:

Replication lag

17. Read/write splitting

Application decides:

Writes:

saveProject()

go to:

Primary database

Reads:

findProjects()

go to:

Replica

Architecture:

Project Service


        |

 +------+------+

 |             |

 v             v


WRITE        READ


Primary     Replica

18. Spring Boot multiple databases

Example:

Primary datasource:

spring:
 datasource:
   primary:
     url: jdbc:postgresql://primary/projecthub

Replica:

spring:
 datasource:
   replica:
     url: jdbc:postgresql://replica/projecthub

Usually implemented with:

  • routing datasource
  • transaction rules

19. Database partitioning

Partitioning means:

Split one table internally.

Example:

Huge table:

events

5 billion rows

Partition by date:

events_2026_01

events_2026_02

events_2026_03

Query:

WHERE date='2026-02-10'

Database only checks:

events_2026_02

20. Partitioning vs indexing

Index:

Find rows faster

Partition:

Reduce the amount of data searched

They solve different problems.

21. Sharding

The big one.

Sharding means:

Split data across multiple databases.

Example:

Users:

Database 1

users 1-1,000,000
Database 2

users 1,000,001-2,000,000

Architecture:

                Application


                    |

               Sharding Logic


        +-----------+-----------+

        |                       |

        v                       v


    Database A             Database B

22. Sharding key

You need a rule.

Example:

user_id % number_of_shards

Example:

3 databases:

user_id 10

10 % 3 = 1

Database 1

23. Problems with sharding

Sharding is powerful but difficult.

Problems:

Cross-shard queries​

Example:

“Find all users.”

Need:

Database 1
+
Database 2
+
Database 3

Transactions​

Before:

One database transaction

After:

Multiple databases

Much harder.

Rebalancing​

Adding a new shard:

Before:

3 databases

After:

4 databases

Data movement required.

24. When should you shard?

Usually only when:

  • one database cannot handle the data
  • replicas are not enough
  • partitioning is not enough

Do not shard early.

25. Connection pooling

A hidden database problem.

Every request:

Open connection

Query

Close connection

is expensive.

Instead:

Application

 |
 v

Connection Pool

 |
 +--- connection 1
 |
 +--- connection 2
 |
 +--- connection 3

 |
 v

Database

Spring Boot uses:

HikariCP

by default.

26. Connection pool settings

Example:

spring:
 datasource:
   hikari:
     maximum-pool-size: 20

Meaning:

Maximum:

20 database connections

27. Database transactions at scale

A long transaction:

BEGIN;

update huge_table;

COMMIT;

can:

  • lock rows
  • slow others

Keep transactions short.

28. Event-driven database updates

Instead of:

Project Service

updates:

projects
users
analytics
notifications

Use:

Project Service

updates project


publishes:

PROJECT_UPDATED


        |

        v

Other services update themselves

29. ProjectHub database architecture evolution

Small system​

Project Service

       |

 PostgreSQL

Growing system​

Project Service

       |

      Redis

       |

 PostgreSQL

Bigger system​

             Project Service


                    |

          +---------+---------+

          |                   |

          v                   v


      Primary            Replicas


      WRITE              READ

Very large system​

                Application


                    |

               Sharding Layer


        +-----------+-----------+

        v                       v


    Database A              Database B

30. Production database checklist

Before scaling:

✅ Add indexes
✅ Optimize queries
✅ Use pagination
✅ Add caching
✅ Use connection pooling

Then:

✅ Read replicas
✅ Partitioning

Finally:

✅ Sharding
