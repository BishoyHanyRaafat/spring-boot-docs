  • Lesson 46: Messaging Systems RabbitMQ, Kafka, Events, and Event-Driven Architecture

Welcome to one of the most important concepts in distributed backend systems.

Until now, our services communicated like this:

 id="directcall"

Project Service

       |
       |
       v

Identity Service

This is synchronous communication.

The problem:

If Identity Service is slow or down:

Project Service
        |
        X
Identity Service

Project Service suffers.

Now we introduce:

Asynchronous communication

A service sends a message and continues working.

 id="async"

Project Service

       |
       v

 Message Broker

       |
       v

Notification Service

1. What is a message broker?

A message broker is a system that receives messages from one service and delivers them to other services.

Think of it like a post office.

Sender:

Project Service

sends:

PROJECT_CREATED

Post office:

RabbitMQ / Kafka

delivers it to:

Notification Service
Analytics Service
Search Service

2. Why do we need messaging?

Imagine creating a project.

Without messaging:

 id="withoutmq"

User

 |
 v

Project Service

 |
 |
 +--> Save project
 |
 +--> Send email
 |
 +--> Update analytics
 |
 +--> Update search index
 |
 +--> Generate activity log

Return response

The user waits for everything.

With messaging:

 id="withmq"

User

 |
 v

Project Service

 |
 |
 +--> Save project
 |
 |
 +--> Publish event
 |
 v

Return response


Later:


RabbitMQ

 |
 +--> Email
 |
 +--> Analytics
 |
 +--> Search

Much faster.

3. Event-driven architecture

The idea:

Services communicate through events.

Example:

Project Service says:

A project was created.

It publishes:

 id="event1"
{
 "event":"PROJECT_CREATED",
 "projectId":100,
 "ownerId":5,
 "createdAt":"2026-01-01"
}

It does NOT say:

“Send email.”

It only announces a fact.

4. Commands vs Events

Very important distinction.

Command​

A request to do something.

Example:

CreateProject

Meaning:

Please create a project.

Event​

Something already happened.

Example:

ProjectCreated

Meaning:

A project has been created.

Comparison:

Command:

"Do this"


Event:

"This happened"

5. RabbitMQ

RabbitMQ is a message broker based on queues.

Architecture:

 id="rabbit"

Producer

   |
   v

Exchange

   |
   v

Queue

   |
   v

Consumer

6. RabbitMQ components

Producer​

Creates messages.

Example:

Project Service

Exchange​

Receives messages and decides where they go.

Queue​

Stores messages.

Example:

notification.queue

Consumer​

Processes messages.

Example:

Notification Service

7. RabbitMQ example

Project creation:

 id="rabbitflow"

Project Service


publish:


PROJECT_CREATED


        |
        v


     Exchange


        |
        v


notification.queue


        |
        v


Notification Service

8. RabbitMQ routing

RabbitMQ has routing rules.

Example:

Exchange:

project.events

Events:

PROJECT_CREATED
PROJECT_DELETED

Queues:

notification.queue

analytics.queue

Routing:

PROJECT_CREATED

       |
       +---- notification

       |
       +---- analytics

9. RabbitMQ message acknowledgment

Important.

Imagine:

Notification Service receives:

{
"event":"PROJECT_CREATED"
}

It sends email.

Success:

 id="ack"

Process message

       |

ACK

       |

RabbitMQ removes message

Failure:

 id="nack"

Process message

       X

Error

       |

NACK

       |

Message remains

10. Why acknowledgments matter

Without acknowledgment:

RabbitMQ thinks:

"Message delivered successfully"

and deletes it.

But the service crashed.

Message lost.

11. Consumer retries

Example:

Email sending fails.

Retry:

Attempt 1

X


Attempt 2

X


Attempt 3

OK

But be careful.

What if:

Payment processed

then retry happens?

You might charge twice.

12. Idempotency

Very important concept.

An operation is idempotent if:

Running it multiple times gives the same result.

Example:

Bad:

Charge $100

Twice:

-$100
-$100

Bad.

Good:

Set user status = ACTIVE

Run:

1 time

or:

100 times

Result:

ACTIVE

13. Dead Letter Queue (DLQ)

What happens when a message always fails?

Example:

Email Service

tries

10 times

still fails

Do not keep retrying forever.

Move it:

 id="dlq"

Main Queue

      |
      X

      v

Dead Letter Queue

Later:

Developer investigates.

14. Kafka

Apache Kafka is another messaging system.

But Kafka is designed differently.

RabbitMQ:

Message delivery

Kafka:

Event streaming

15. Kafka architecture

Basic:

 id="kafka"

Producer

    |
    v

 Kafka Topic

    |
    +------ Consumer A

    |
    +------ Consumer B

16. Kafka topics

A topic is a stream of events.

Example:

project-events

Contains:

PROJECT_CREATED

PROJECT_UPDATED

PROJECT_DELETED

17. Kafka partitions

Kafka topics are divided into partitions.

Example:

 id="partition"

project-events


Partition 1

event1
event2


Partition 2

event3
event4

Why?

Performance.

Multiple consumers can process in parallel.

18. Kafka ordering

Kafka guarantees ordering:

Inside one partition.

Example:

Partition 1:

1. ProjectCreated

2. ProjectUpdated

3. ProjectDeleted

Order preserved.

Across partitions:

No global order.

19. Kafka consumer groups

Example:

Three notification servers:

 id="consumer"

Notification Service


Consumer Group:

notifications


Instance 1

Instance 2

Instance 3

Kafka distributes messages.

RabbitMQKafka

ReplayLimitedExcellent

22. Event schema design

Bad:

{
"user":"Ahmed created something"
}

Hard to process.

Better:

{
 "eventId":"abc-123",
 "eventType":"PROJECT_CREATED",
 "version":1,
 "timestamp":"2026-01-01T10:00:00",
 "data":{
    "projectId":10,
    "ownerId":5
 }
}

23. Why event versions matter

Today:

{
"projectId":10
}

Tomorrow:

{
"projectId":10,
"teamId":20
}

Old consumers may break.

Use:

{
"version":2
}

24. The Outbox Pattern

A very important production pattern.

Problem:

You do:

 id="dualwrite"

Save project

+

Publish event

Two operations.

What if:

Database succeeds:

Project saved

but:

RabbitMQ fails:

Event not published

Now inconsistent.

Solution:

Outbox pattern.

Architecture:

 id="outbox"

Project Service


      |

      v


Database


projects table

+

outbox table


      |

      v


Message Publisher


      |

      v


RabbitMQ

Flow:

Transaction:

BEGIN;

INSERT project;

INSERT outbox_event;

COMMIT;

Now both are saved.

A background worker publishes:

outbox_event

      |

      v

RabbitMQ

26. Common messaging mistakes

Mistake 1​

Using events for everything.

Bad:

Need user name?

Publish event

No.

Use REST.

Mistake 2​

No retry strategy.

Messages fail.

You need:

  • retry
  • DLQ
  • monitoring

Mistake 3​

Ignoring duplicate messages.

Consumers must handle:

same event twice

Mistake 4​

Huge events.

Bad:

{
"allProjects": [
100000 items
]
}

Events should be small.
